# Desktop architecture

## Ownership

The files under `crates/pi_desktop/src/desktop/` implement separate owners, not extensions of one mutable window object:

```text
Desktop (desktop.rs): window layout, pane resizing, theme and global shortcuts
  ├─ Prefs (prefs.rs, a GPUI global): the app's own preferences and remembered state
  ├─ WorkspaceController (workspace.rs): stable session IDs, selection, saved catalog
  │    └─ SessionTab per open session
  │         ├─ SessionController (session.rs): model, RPC client/task, request policy, LSP bridge
  │         └─ SessionView (session_view.rs): composes this session's UI
  │              ├─ TranscriptView: activity projection, Markdown, expansion, virtual list/scroll
  │              ├─ DiagnosticsView: lazy selectable session diagnostics
  │              ├─ ComposerView: editor, draft, attachment, slash/picker/@ mention state
  │              ├─ TreeView: filtered entry projection, vector graph, selection/labels
  │              ├─ ChangesView: immutable per-turn jj diffs and file selection
  │              ├─ ContextView: reported usage, compaction/settings and retry projection
  │              ├─ FilesView: editor tabs, file-tree filter, save/close/conflict UI
  │              ├─ TerminalDrawer (terminal.rs): this session's shells, tabs, height
  │              └─ InspectorView: independently subscribed active-page inspector
  ├─ SidebarView: search, project expansion, workspace navigation
  ├─ HeaderView: title, search field, window controls
  ├─ StatusBarView: connection and selected-session summary
  └─ App views: SessionsView, SettingsView, Models/Resources CatalogView + CatalogInspector
```

`SessionController` exposes the pure `pi_core::Session` through a read-only accessor. Views send typed `Command` values or call submission/queue methods; they cannot mutate its model directly. The runtime owns bootstrap tracking, expected resume identity, pending submissions, and the clear-before-abort transaction. It owns no editor, Markdown entity, or scroll handle.

`WorkspaceController` allocates monotonic local `SessionId`s, independent of vector positions and RPC request IDs. It retains each session's runtime and view handles. Saved catalogs are merged/deduplicated when they change or selection changes, rather than on every window render. The sidebar displays all open sessions under ACTIVE and project-scoped rows in the PROJECTS tree.

Composer drafts are the contents of each session's own `TextInput` entity. There is no shared editor to swap or a window-global slash stash. Deactivation closes menus and restores a stashed draft in that same composer. Rejected submissions and recovered queue text are routed back through the originating controller, even if another session is selected. Transcript expansion, document identities/code-block state, scrolling, and composer expansion stay with the session. Text selection follows normal Markdown focus/mouse behavior.

`pi_core` remains GPUI-independent. Process/framing/correlation mechanics stay there; the desktop controller implements application-level lifecycle policy. The demo adapter in `desktop/demo.rs` supplies fixture and simulated records through the same reducer without starting a process or calling a model.

## Diagnostics

`SessionController` owns an in-memory diagnostic ring (128 entries / 48 KiB), separate from conversation content. It records executable identity (not arguments/environment), RPC command names and IDs, response success/failure, request/protocol failures and process exit. Exit includes the transport's bounded 8-KiB stderr tail, not a complete subprocess transcript. Common credential-like lines are redacted, but arbitrary stderr/errors may still be sensitive; the UI warns before copying. Request bodies and model/tool payloads are not logged.

`DiagnosticsView` subscribes to diagnostic changes and parses its selectable document lazily when visible. The error banner shows only a summary with View details/Copy diagnostics; the inspector exposes newest entries first and supports clearing/copying. The header ellipsis and Ctrl+Shift+D open the same per-session view. Dismissing a banner does not erase diagnostics. Logs are not persisted or automatically uploaded.

## Updates and rendering

- Controllers emit `SessionEvent`s: targeted change flags, message/tool content changes, request completion, draft recovery, and an explicit reveal-tail request. Pipe events no longer call into `Desktop`.
- Workspace navigation uses small cached `Summary` values. A text delta that does not change a summary does not invalidate the sidebar or header. Background content marks that session's transcript dirty without parsing the active session's documents.
- Composer input, picker hover/filtering, and slash selection notify the composer, not the window or transcript. Model choices and grouped slash rows are cached between query/catalog changes.
- The transcript uses GPUI's variable-height `ListState`; model/thinking choices use `uniform_list`; the grouped slash menu uses a variable-height list. Only visible rows and overdraw are constructed. Transcript history and RPC catalogs still remain in memory; this is rendering virtualization, not process/history eviction.
- Content events mark the affected message dirty. The visible row synchronizes its Markdown sources when rendered, coalescing multiple deltas before that render. Metadata-only events do not resynchronize documents. Existing Markdown entities are updated in place, preserving selection and code-block state. Tool output uses plain-text mode with whitespace and URL links preserved.
- Each Markdown block has a distinct focus/key-dispatch node. Selection and copy handlers must not share the surrounding message row's node; a later block could otherwise receive a selected block's copy shortcut after cached-frame reuse.
- `transcript/activity.rs` groups adjacent tool/thinking blocks across assistant messages, never across visible prose, user messages, errors, or jj footer boundaries. Settled activity defaults to one collapsed row even when calls failed; live and unfinished calls default open. Headers retain a warning marker and failure count for errors, or a green check once all calls have completed successfully and the run has settled. Counts/status come from actual tool records, not generated summaries. Explicit disclosure and selection pin activity open through settlement; reveal-from-Changes opens the containing activity too. Prose, tools and the composer use the available width without a fixed reading cap.
- Tool details start collapsed. Their document sources are created only when expanded. Edits use selectable diff/before/after code, writes show their requested content, and bash shows command and output. A shared field projection drives both rendering and copy actions, avoiding non-selectable decorative diff rows. Literal code is fenced safely even when tool content contains backticks; copy actions exclude the added fence. Previews are bounded by 500 lines and 64 KiB, while the header menu can copy the full retained value.
- Streaming and expansion remeasure affected rows without discarding the scroll anchor. Live threads follow the tail until the user scrolls away. Sending explicitly reveals the tail. Offline fixture sessions initially show the top for deterministic previews.
- Sidebar, header, inspector, status bar, and transcript have explicit GPUI cached-view boundaries with definite layout sizes. The returned root of a cached view must fill those bounds too; allocating a width on the wrapper alone does not stretch its contents. The composer is measured dynamically as its editor grows. `TextInput` publishes its wrapped viewport, overflow and offset through a session-local `ScrollableHandle` to the shared native scrollbar. A stable gutter prevents the thumb from covering text or changing wrapping when it appears. Manual wheel/thumb scrolling suspends caret following; text edits and cursor navigation resume it, including across editor resizing.
- Focus changes, theme changes, resized bounds, and running animations can legitimately cause rendering. Tests assert isolation for stable-bounds typing/hover/filter updates, not zero rendering under every interaction or a particular frame rate.
- Zed Markdown, code blocks, menus, scrollbars, and tooltips read Zed's global theme. `markdown_view::sync_theme` mirrors the app palette into it when the theme changes.

There are no strong parent/back-reference cycles: session views reference their controller, workspace owns session handles, and subscriptions/tasks target weak receivers. A tool context menu captures a weak reference to its own controller rather than a window plus mutable active-session index.

## Landing, review and navigation lifecycle

- `LandingView` owns its scroll and catalog subscription. Starting-point chips emit an event to the owning session's composer: they preserve the draft and focus it, but never submit. Unknown context manifests/tool inventories remain explicitly unavailable. The pre-session inspector shows reported model/provider/context-window/thinking and project/session metadata rather than empty usage counters.
- All tool calls are 24px borderless rows. Result/diff/command documents are only retained while explicitly expanded; selection, full-value copy and streaming updates remain available.
- Thread Overview combines jj history with context and session usage. Changes uses the workspace study's 240px turn/file list, compact file header and numbered diff, plus file/turn actions in the inspector. Cache hit percentage is **token reuse**, `cacheRead / (input + cacheRead + cacheWrite)`, never an invented count of hit requests or per-file cost.
- Zed's `git_ui::ProjectDiff` is tied to its Workspace and live Git repositories. Our immutable jj/legacy projection instead reuses the retained selectable Zed Markdown/code surface. `diff_preview.rs` derives aligned old/new numbers from hunks, or parses the line positions Pi's edit tool actually reports (including offset changes across skipped context). Unnumbered snippets stay unnumbered. Copy Diff retains the original patch, without the display columns; previews are not promised to be apply-ready.
- A legacy session can have no turn associations even in an existing jj repository. Successful edit/write calls without recorded tool IDs stay in a separate incomplete section. Recording a new turn captures its tool IDs; matching file paths alone never hide older edits. Shell/external changes cannot be reconstructed from that fallback; undo/redo is only for actual recorded turns.
- `WorkspaceController::selected_project` is independent of the active session. Selecting a project does not launch a process. It is retained after its last session closes; New Session uses it, including from `WelcomeView`. Removing that project clears/falls back the choice. The sidebar geometry remains unchanged: close marks replace, rather than overlap, time/count labels on hover.
- Close requests are confirmed for running agents, drafts/queued work, unsaved editor buffers, project removal and hiding saved sessions. File mutations, jj operations and exclusive navigation/fork work must settle before close. Confirmation rechecks the target set and guards. Closing stops/reaps the owned RPC child before reopening can reuse its file. Shared editor buffers open elsewhere remain. No project directory or saved JSONL is deleted; hidden catalog/project rows are suppressed only for the current app run.

## New-session chooser

`new_session.rs` owns the projects-study form and its inputs/subscriptions. Preview/cancel launches no backend. Project/folder selection, explicit Git worktree creation and initial-model selection stay local until Create succeeds. Git uses bounded background argv execution, a new branch/nonexistent absolute target, no force/overwrite/deletion and retained partial results. The captured model is applied with `persist: false` only after the new controller's identity-critical bootstrap.

The initial-model picker is a searchable, keyboard/click-away floating overlay using reported models/current-model fallback or configured default. It inherits the established palette and never resizes the dialog. It is an anchored final sibling inside the native prompt overlay, **not `gpui::deferred`**: GPUI prepares normal deferred draws before preparing its native prompt, so Deferred inside the prompt caused “must call prepaint before paint.” The fix changes the desktop only. Picker bindings are registered after TextInput/desktop bindings with the descendant filter context.

The footer's process popup projects existing owned PID/state/session metadata only. Memory is explicitly unreported, and idle RPCs remain until their sessions close. Its viewport-bounded row list has the shared always-visible overflow scrollbar and a stable 14px gutter, while header/footer remain fixed; wheel, thumb drag and track clicks scroll only rows.

## Standalone SDK backend (trial)

`packages/pi-desktop-backend` can replace the patched source launcher through the existing `PI_DESKTOP_RPC_ENTRY` override, or run built into the app (see Built-in backend); no Rust ownership boundary changes. Each session's RPC subprocess owns one Pi SDK `AgentSessionRuntime`. It speaks the existing JSONL command/response/event protocol and rebinds subscriptions/extensions after session replacement. The old source launcher remains available. Builds without the `bundled-backend` feature (development and tests) still default to `pi` from PATH; release packaging turns it on.

The inspector receives optional `get_state.activeTools` metadata from the public SDK tool registry/loadout APIs, showing names only and retaining reported descriptions/origins in hover tooltips. Older backends that omit it remain explicitly unknown; historical tool calls are not an inventory. State refreshes at run boundaries, handled commands and explicit reload keep it current without another process. The project TPS extension's info notification is recognized narrowly and retained verbatim in the bottom status bar, with the full data in a tooltip; warnings/errors and unrelated notifications remain notices. Run metrics are session-local and cleared when the next run starts.

The npm SDK is pinned to the published Pi 0.87.1 artifact, with a shrinkwrapped dependency graph. Private imports live only in `compat.mjs`: Pi's trust resolution, model scope, event serializer, stdout guard, HTTP setup, built-in extensions and branch share exporter are reused instead of duplicated. The released SDK's boolean preflight callback is adapted through a temporary session-local observation of its agent-entry method. Handled extension work does not imply a new submitted-prompt run; actual completion still comes from `agent_settled`. `fork` takes an optional `cwd` (reported as the `fork_cwd` feature in `get_backend_info.features`): the new session file's header names that folder and the process keeps its session. `append_custom_entry` and `get_custom_entries` keep the desktop's own records, such as turn links. Each session asks `get_backend_info` once, as optional metadata; Settings → General → Backend shows the answer (backend, pi, protocol and Node versions). Plain `pi --mode rpc` answers "Unknown command", which `pi_core` records as `BackendInfo::Unsupported` instead of an error.

The backend bounds LF-framed UTF-8 records, pending output and request concurrency. Mutations/preflights are serialized; extension dialog replies bypass the gate, and metadata/Abort remain responsive. Saved trust does not silently change process trust. Package operations require explicit commands and do not implicitly reload. The adapter only deletes saved sessions through Trash, never a silent permanent-unlink fallback.

Headless sharing calls Pi's own branch exporter and credential resolver, then uploads to Radius or creates a private gist using argv-based `gh` invocation. It returns the desktop's structured share result, supports cancellation and removes temporary files. Sharing is explicit and potentially exposes conversation data; native auth remains a terminal handoff. Live provider streaming, real uploads, remote installers and native macOS/Windows are not yet validated. See the [backend README](../packages/pi-desktop-backend/README.md) for supported startup options and limits.

## Built-in backend

Release builds can carry pi-desktop-backend inside the `pi-desktop` executable, so users install neither Node.js nor pi.

- **Standalone build.** `packages/pi-desktop-backend/scripts/build-binary.mjs` compiles `src/binary.mjs` with `bun build --compile` (tested with Bun 1.4.2) into one executable, the way pi builds its own release binary. The entry runs pi's Bun setup from the npm SDK (`dist/bun/sandbox-env-setup.js`, `dist/bun/runtime-setup.js`), then `cli.mjs`. User extensions load from pi's embedded modules, as in pi's binary. `.env` and `bunfig.toml` autoloading are off, since Node never reads them.
- **Why the private imports are literal paths.** `compat.mjs` used to build them at run time (`import(new URL(path, entry))`) and read pi's `package.json` from disk. A bundler cannot follow either, so the binary started and failed at the first private module. Each is now an `import()` of a literal `../node_modules/@earendil-works/pi-coding-agent/dist/...` path, and the version check imports `package.json`; Node runs the same code.
- **Files beside the executable.** pi finds its themes, export template, docs, examples, image `.wasm` and `package.json` next to its executable, so the build puts the same files there as pi's `scripts/build-binaries.sh`. Bun's `--asset` could embed them, but pi would then need `PI_PACKAGE_DIR`, which every command pi runs would inherit. The build writes that folder as a zstd-compressed tar (about 35 MB for linux-arm64; the folder is about 100 MB).
- **Embedding.** The `bundled-backend` cargo feature includes the archive named by `PI_DESKTOP_BACKEND_ARCHIVE`; `build.rs` names it by a hash of its bytes. Without the feature (development and tests), nothing is embedded.
- **Unpacking.** `bundled_backend::unpack` runs once in `main`, before the window. It unpacks into `<cache>/pi-desktop/backend/<hash>/` unless that folder already has the executable, through a temporary folder renamed into place, and removes other builds' folders. The first launch of a build takes a fraction of a second; later launches only check a file. A failure is logged and sessions fall back to `pi` from PATH.
- **Launch order.** `PI_DESKTOP_RPC_ENTRY` / `PI_DESKTOP_PI`, then Settings → General → Backend, then the built-in backend (`Prefs::bundled_backend`, used by `prefs::backend`), then `pi` from PATH.
- **Runtime.** The binary runs on Bun's Node.js compatibility. `get_backend_info` adds `bunVersion`, and Settings shows "Runtime: Bun …, built in" instead of the Node.js version. In this sandbox it answers its first command in about 0.2 s, where `node src/cli.mjs` takes about 8 s on the shared mount. The backend suite passes against it (`PI_DESKTOP_BACKEND_BINARY=… npm test`).
- **Still needs the machine's tools.** Signing in runs `pi /login` in a terminal, so it needs an installed pi. Installing npm pi packages runs `npm`, git packages run `git`, and npm-based language servers need Node.js. An extension with a native Node add-on may not load under Bun, as in pi's own binary.
- **Signing.** Bun signs the executable ad hoc, like the rest of today's development packages. With `PI_DESKTOP_CODESIGN_IDENTITY`, the build signs it with that identity for the hardened runtime and `packaging/macos/backend.entitlements`, the entitlements Bun's documentation lists for compiled executables (JavaScriptCore compiles code at run time), before it is packed. It keeps that signature when unpacked. Files the app writes itself are not quarantined, so Gatekeeper does not check them.
- **Packaging and CI.** `scripts/package-{linux,macos}.sh` and `package-windows.ps1` run `npm ci` and `build-binary.mjs` for their platform into `artifacts/backend/`, build with `--features bundled-backend`, and pass the notices to `package_desktop.py --notices`. CI's release jobs do the same with Node.js 22.19 and Bun 1.4.2. The checks job builds the linux-x64 binary, runs the backend suite against it and runs clippy with the feature.
- **Licenses.** Packages add `licenses/BUN-LICENSE.md` (Bun links JavaScriptCore, LGPL-2), `licenses/PI-MIT.txt`, and `PI-DESKTOP-BACKEND-NOTICES.txt`: every production package in the backend's `npm-shrinkwrap.json` with its license file, or its declared license when it has none (46 of 230 have none).
- **Not done yet.** The login terminal still runs `pi`. The hosted CI jobs, Developer ID signing and notarization, and the backend on macOS and Windows have not run.

## Protocol and submission policy

- Commands have unique IDs within a process. The transport matches responses by ID **and command**, not arrival order. Late responses after a timeout are ignored. Timeout means the outcome is unknown, not that execution definitely failed; prompts are never retried automatically.
- Strict LF JSONL accepts CRLF and treats Unicode separators as ordinary text. Invalid, unterminated, or oversized records are visible errors. Maximum record size: 16 MiB.
- Read/write queues are bounded. UI sends use `try_send`, not a blocking pipe write. Stdin, stdout, and stderr work happens off the foreground executor; stderr is a bounded diagnostic tail, never protocol input.
- Bootstrap requests state, messages, statistics, and saved sessions before enabling submission. The command catalog is also requested at startup for the landing cards, but is not an identity-critical bootstrap gate. The requested saved-session ID is stored separately from mutable RPC state and checked during resume. Failed/partial bootstrap does not enable prompts or state-changing commands. Metadata queries and explicit stop/queue recovery remain available.
- Streaming deltas update blocks by `contentIndex`; block-end and message-end payloads replace partial content. Tools are keyed by `toolCallId`; history and live events use the same reducer.
- Prompt acknowledgement is not completion. Only `agent_settled` ends a live run; `agent_end` may precede retries, compaction, or continuations.
- `queue_update` replaces displayed queues. Stop serializes `clear_queue` → successful response → `abort`, recovering the returned text to the originating composer. A Stop during an outstanding queue-only clear upgrades that transaction to abort after success. Clearing failure does not blindly abort with queued work still present.
- `bash` is explicit SDK-owned shell work, separate from agent prompts: `!` includes output in context, `!!` excludes it. Correlated live previews retain a UTF-8-safe 64-KiB tail; final history/results come from the SDK. Stop/disconnect/shutdown handle the shell state without fabricating agent lifecycle.
- Requests have deadlines except completion-style commands (`compact`, `reload`, `navigate_tree`, `fork`, `bash`). Navigation summarization can make model calls and defaults off.
- Tree uses append-only `get_entries`, stable IDs and parent edges, including abandoned branches. Filtering reconnects visible descendants to their nearest visible ancestor; labels/settings are not counted as extra conversation branches. The native renderer draws connected rails and vector node shapes rather than font glyphs.
- Context usage is RPC `contextUsage`, not lifetime token sums. Exact prompt assembly/context manifests are unavailable and are not reconstructed from guessed files. Changes prefers recorded jj turn snapshots; the no-jj fallback explicitly says it contains only observed successful edit/write calls, not shell edits.
- Unknown events/fields are tolerated. Extension-augmented message/tool payloads retain JSON values; screen commands, state, catalogs, and statistics use typed structures.
- `/compact`, `/copy`, `/name`, `/new`, and `/reload` map to local actions or RPC commands. Pi commands with the same name take precedence when typed. Other slash commands are sent as prompts for Pi to expand or execute.

## Process ownership

Selecting another session never repurposes a child underneath an active run. An existing tab is selected by identity, or a new controller starts Pi with the saved session's cwd and `--session` path. The application does not reimplement Pi's session store or grant project trust.

On shutdown, stdin closes first. An uncooperative child is killed and reaped after a two-second grace period. Unix children use isolated process groups; Windows children use kill-on-close Job Objects. Descendants stop before pipe-reader joins because they may inherit stdout/stderr. `RpcClient::drop` joins its supervisor. Closing/reaping many clients remains sequential and may briefly block the foreground thread; asynchronous grouped teardown remains a follow-up.

## jj (`pi_jj`)

`crates/pi_jj` makes each agent turn that edits files its own jj change. It is GPUI-independent; the session controller drives it (see "jj in the app" below). It uses `jj-lib` pinned to an exact version (0.45.1), so no `jj` binary is needed. Calls block on jj-lib's async API; the app must run them off the UI thread and only between runs.

- `detect(path)` finds the nearest `.jj` or `.git` above a project folder. `Project::init` is the explicit opt-in: it colocates with an existing `.git`, or creates one, and refuses inside a linked git worktree.
- jj records files, not conversation. Rewinding the conversation is pi's `/tree`, which moves within the session and leaves files alone; `pi_jj` only records what a turn did to the files.
- `begin_turn(prompt)` writes no change. It snapshots, so edits already on disk are recorded before the turn (an operation only if something changed since jj last looked), and remembers the working-copy commit.
- `end_turn` snapshots again and compares with that commit. If the files are the same, it writes nothing: a read-only turn leaves no change and no operation. Otherwise one operation, `pi: record turn`, splits the working copy. The pre-turn state keeps its change, the turn's edits become a change on top described with the prompt, and a new empty working copy goes on top of that. If the working copy was empty and undescribed, the turn takes over that change instead of leaving an empty change under it. If the working copy moved to another change during the run (for example a `git commit` or `jj new`), the edits stay in the working copy and `end_turn` reports it rather than guessing a split.
- `changes(change)` diffs a turn against its parent: status, line counts and unified hunks for the Changes tab. Files changed by shell commands are included because this is what jj recorded, not what tool calls reported.
- `undo_turn` abandons the change. Its edits leave the files, and later changes are rebased onto its parent. If a later change edits what the turn edited, rebasing would put conflict markers in files, so undo is refused with `UndoConflict` naming those changes and nothing is written; undoing the later turns first works. A turn nothing depends on undoes alone. `redo(undo_op)` restores the view from before the undo, like `jj undo`, but only while the undo is still the latest operation. Once anything happened after it, including an edit on disk, redo is refused, because restoring would discard that work.
- `undo_turns(changes)` abandons several turns in one operation, which one redo brings back. `undo_turn_keeping_conflicts(change)` abandons a turn although later changes build on it: they keep jj's conflict, so nothing is lost, and it returns the working-copy files that now have conflict markers.
- `restore_file(change, path)` puts one file of a turn back as it was before the turn (`restore_tree` from the parent), then rebases later changes. Like undo, it is refused with `UndoConflict` when a later change edits the file too.
- `recorded_turn(change, commit)` looks up a turn recorded in an earlier run: the change's visible commit, else the recorded commit, which stays readable after an undo hides it.
- `operations(limit)` lists the operation log newest first (first parents), with each operation's time and a kind from its description: `pi: …` (the app), snapshots, `import git …`, anything else. `operation_files(op)` is what restoring to it would change in this workspace's files; `restore_operation(op)` is `jj op restore`, after recording the files on disk, so it can be restored away again.
- `take_snapshot`, `changed_since(snapshot)` and `restore_paths(snapshot, paths)` record the files before and after one command and put its paths back, as `jj restore --from` does; the result is an edit in the working copy.
- `log_text`, `diff_text(revision, path)` and `show_text(revision)` answer pi's jj tools in plain text, as `jj log`, `jj diff` and `jj show --stat` print it, capped at 48 KiB. A revision is what the CLI takes: a change ID or prefix, a commit ID, `@`, a bookmark.
- `annotate(path, text)` runs jj's line annotation over the working copy's mutable ancestors for the text as the editor has it. Only changes pi recorded count as turns (`pi: record turn …` in the operation log, from any session); other lines have none.
- `add_workspace(path, before)` is `jj workspace add` into an empty folder, with the files as they were just before the change `before`, or as of the last recorded turn (edits not yet in a turn stay behind). `bring_in(workspace)` rebases another workspace's own turns onto this working copy's parent and this working copy onto the last of them, so this folder gains their edits; conflicts stay in jj.

Each operation repeats what the jj CLI does around a command. It reloads the latest operation (another session or the jj CLI may have written since), takes the git import/export lock, imports git HEAD (following a `git commit` or `git checkout` made outside jj), snapshots with the user's ignores, `snapshot.auto-track` and `snapshot.max-new-file-size`, and imports git refs. It then runs one transaction, moves git HEAD to the working copy's parent, exports refs, and checks out the result. In colocated repos, `git log` therefore shows each finished turn as a commit. Settings are loaded like the CLI's: jj-lib defaults, user config files (`JJ_CONFIG`, `~/.jjconfig.toml`, `<config dir>/jj/config.toml`, `conf.d`), per-repo and per-workspace config from the user config directory, then `JJ_*` overrides, resolving conditional scopes. Tests use an isolated environment so a developer's jj or git config cannot affect them.

Known gaps in the spike:

- **Immutability is stricter than the CLI.** It covers the root, tags, and everything on a remote, while the CLI default is `trunk()` plus untracked remote bookmarks. Revset aliases are not read.
- **`remotes.<name>.auto-track-bookmarks` is ignored** on import.
- **A stale working copy is an error,** not repaired.
- **No rename detection:** a moved file shows as deleted plus added.
- **Edits made while pi runs join the turn.** A snapshot cannot tell who changed a file, so edits made during a run by you, an editor or another agent in the same folder are recorded in that turn, and undoing the turn reverts them too. Separate workspaces for parallel sessions avoid this for sessions.
- **A workspace whose working copy another workspace rewrote is stale,** for example after Bring turns in; its session should be closed.

Cost, measured in the Linux dev container:

- jj-lib adds 84 crates, mostly `gix`.
- It raises shared crates to newer semver-compatible releases, among them `chrono`, `thiserror`, `tracing`, `toml_edit` and `rayon`.
- A clean debug build of `pi_jj` and its dependencies takes about 1m50s.

The `jj` CLI 0.45.1 reads repos written by `pi_jj`, and `jj undo` works on its operations (`the_jj_cli_and_pi_jj_share_a_repo`, which runs when `PI_JJ_CLI` points to a jj binary). Run it again whenever jj-lib is upgraded.

### jj in the app

- Opening a live session calls `pi_jj::detect` on its folder. A jj workspace opens in the background; a git-only project shows a banner offering jj ("Not now" / "Turn on jj"); nothing is initialized without that click. The banner is skipped when `jj.offer` is `never` for the project, or when "Not now" was answered for that repository root in an earlier launch (`general.rememberDismissed`, kept in `state.json`). Turning jj on detaches git HEAD, which then follows jj's commits; branches stay where they are.
- `SessionController` owns one `pi_jj::Project` per session behind `Arc<Mutex<_>>` and runs every call on the background executor. Submitting a prompt that starts a run first runs `begin_turn`, then sends the prompt, so pi cannot write before the files are recorded; the composer shows the run as working meanwhile. `agent_settled` runs `end_turn`, then `changes` for the counts.
- A turn that changed files gets one line under the run's last message: its change ID, file count and `+/−` lines, with Diff and Undo on hover. An undone turn shows what was restored and Redo. Buttons are hidden during runs and while a jj call is running. Failures, including a refused undo, appear as the session notice.
- Turn diffs/descriptions stay in memory for Changes. Conversation hydration invalidates transcript indexes without deleting the file-history records; each record finds its line again by the `timestamp` of the message it sits under (`reanchor_records`, after the model applies `get_messages`), and a message not in the current branch leaves the record in Changes only. Branch navigation does not rewind files. Undo/redo also refuses while a shared editor project has unsaved buffers.
- **Turn links** (`desktop/turn_links.rs`, design study 05 decision 1) keep the file history in the session file. Recording a turn, undoing it and redoing it each append a `custom` entry of type `pi-desktop-turn` through the backend's `append_custom_entry`: `{"event":"record","change","commit","after","tools"}`, `{"event":"undo","change","operation"}` or `{"event":"redo","change"}`, with jj ids in hex and `after` the anchor message's time in ms. pi keeps these out of the model's context and copies them into forks. When a session starts, `get_custom_entries` reads them from all branches; `replay` gives each turn's last state, and once the jj project is open `Project::recorded_turn` looks each one up (the change's visible commit, else the recorded commit, which stays readable after an undo). A hidden turn without an undo of ours was abandoned outside the app and is dropped; nothing is guessed from filenames. Only `turn_links.rs` knows the encoding, so another agent needs only another store. Plain `pi --mode rpc` has neither command: the diagnostics say so and the history lasts until the session closes. Tree lists these entries (kind `desktop`) only under All. `pi_core` now gives custom messages from `entry_appended` pi's timestamp too, so a line under the run-end language-server message anchors the same live and after reload.
- **Restore file** (study 05, decision 2): Changes' inspector button and the diff's `[ RESTORE FILE ]` ask first, then run `restore_file`; the turn's record keeps its other files. A later turn that edits the file blocks it with a notice naming that turn.
- **Undo with conflicts** (decision 10): a refused undo asks "Later changes build on turn …" with **Undo and draft a fix** (`undo_turn_keeping_conflicts`; the composer gets a drafted prompt such as "Resolve the conflict markers in @a.txt left by undoing turn kqxlmwsv (“…”). Keep what the later changes did.", which the user reads and sends), **Undo N turns** (only when every later change is one of this session's turns and your current edits are not among them), or Cancel. Redoing any turn of a several-turn undo brings back all of them.
- **Operations** (decision 11): Changes has TURNS and OPERATIONS tabs. Operations loads the log off the UI thread when shown and after jj work; a row shows the operation, and the inspector what restoring to it would change and **Restore project to …**, after a confirmation. Turns a restore hid show as undone; their Redo undoes the restore.
- **Snapshots around commands** (decision 3, `jj.snapshotBeforeCommands`, on by default): the extension's `tool_call` hook asks the bridge for `snapshot_before` and waits, so `bash` starts after the snapshot; `tool_result` asks for `snapshot_after`. A command that changed files gets an amber "changed N files" pill on its row (the files in its tooltip) and, on hover, **Restore to before**, which asks first and runs `restore_paths`. pi runs a batch's tool calls in parallel by default, and all their `tool_call` hooks run before any of them: "before" is before the whole batch, and "after" can include another tool's edits from it. Kept in memory while the session is open. The snapshot cost in large repositories is not measured yet.
- **jj tools for pi** (decision 12, `jj.tools`, off by default, per project): a session starts with `PI_DESKTOP_JJ_TOOLS=1`, and the extension registers read-only `jj_log`, `jj_diff` and `jj_show`, which the bridge answers from the session's project. Errors come back as text for the model.
- **Turn bars** (decision 7, `jj.turnBars`): while ⌥ (Alt) is held over a file tab, `annotate` runs off the UI thread on the buffer's text and `pi_editor::mark_rows` draws gutter bars, accent for this session's turns and steel for other sessions'. ⌥-click is caught before the editor (where Alt-click adds a cursor) and opens a card with the change, turn, prompt and line count, **Show in thread** and **Diff**. The file tab's footer says "⌥ shows which turn wrote each line" (Alt off macOS) when the session has jj, and while ⌥ is held shows the legend instead: this session, other sessions, no bar for you or before jj, ⌥-click. Unit tests cannot run editor services; bars, their release, the card and the footer were checked in the app under Xvfb with a scripted pi, and the user confirmed ⌥ and ⌥-click on macOS.
- **Parallel sessions** (decision 4, `jj.parallelSessions`): `parallel.rs` tracks which sessions are working, by jj workspace root. A not-started session's first prompt while another session works in the same root: `same` sends it, `workspace` makes the automatic workspace, `ask` shows a form (a custom prompt, like the new-session form): own workspace in `<parent>/<name>-ws/<first words of the prompt>`, own workspace in a chosen empty folder, or same folder, and "Remember for this project", which writes `.pi/pi-desktop.json`. Choosing a workspace runs `add_workspace`; the workspace controller opens a session there with the prompt, sent once it is ready and its jj project is open, and closes the one that asked.
- **Bring turns in**: a session in such a workspace shows **Bring turns into …** in Changes. After a confirmation it runs `bring_in` on the main folder, refused while a session works there. The main folder is known from the move, or after a restart from the `<main>-ws/<name>` layout.
- **Fork with the files** (decision 5): Tree's Fork asks only when one of this session's turns (not undone) was recorded after the entry and the backend reports `fork_cwd`. **As at this entry** makes a workspace with the files from before the first later turn and forks with `cwd`, so the new session file's header names the workspace; **As they are now** is the ordinary fork. With plain pi it forks without asking.

## Terminal (`pi_terminal`)

`crates/pi_terminal` runs shells with Zed's `terminal` crate (alacritty's emulator on a PTY) and draws them with a view and element of its own. Zed's `terminal_view` cannot be reused: its element and view need a `Workspace`, `Project` and `editor`. `element.rs` is adapted from Zed's `TerminalElement` (grid layout, batched text runs, background and block-glyph rectangles, IME, pointer and scroll input) without the workspace, inline mode, blocks below the cursor, search or hover tooltips; it paints the cursor and selection itself instead of using `editor`. `TerminalView` owns focus, keys, IME text, the clipboard and scrollback.

- `spawn(cwd)` starts the user's login shell (`$SHELL`) in the session folder, with the app's environment plus `TERM=xterm-256color`; the PTY opens off the UI thread. A missing folder is an error, because the PTY would otherwise start in the app's own folder.
- Cell colors come from Zed's theme, whose `terminal_*` colors `markdown_view::sync_theme` sets from the Evening/Moonstone palette, like the Markdown colors. Font, cursor, selection and link colors are the `TerminalStyle` global, set in the same place.
- Keys: GPUI dispatches key bindings before key-down handlers, and bindings in an enclosing context still match. The app binds Enter (submit), Escape (stop), Up/Down, Tab and, on Linux and Windows, `ctrl-b/j/k/n/o/q` in `Desktop` or globally. The `Terminal` context binds those keys to `SendKeystroke`, so they reach the shell; the innermost context wins. Copy, Paste, Select All and Clear use Cmd on macOS and Ctrl+Shift elsewhere, as in Zed.
- The tab name is the shell (`zsh`) at the prompt and the foreground program (`npm`) while a command runs, with a busy dot. The foreground process group is compared with the shell's pid; the name refreshes on the terminal's `TitleChanged`.

### Terminal in the app

- Each `SessionView` owns a `TerminalDrawer`. It sits at the bottom of the session column, under the composer on the thread page and under Changes, Tree, Context or a file tab otherwise. Shells keep running while the drawer is hidden or another session is selected; closing the session drops them, and dropping a `Terminal` ends its shell. Terminals are not part of pi's context.
- **Ctrl+`** and **Cmd+J** (Ctrl+J on Linux and Windows) toggle the drawer: show it (starting a shell if none), focus it when it is shown but not focused, hide it when focused. Backtick is a dead key on many keyboard layouts, hence the second shortcut. On Linux and Windows, Ctrl+J inside a terminal goes to the shell (it is Enter there), so Ctrl+` hides a focused drawer. A terminal button at the right of the session tab bar shows or hides the drawer whatever has focus. Hiding a focused drawer returns focus to the composer.
- Tabs: **+** starts another shell; a tab's × or a middle click closes it and ends its shell; `exit` closes its tab too. The last tab closing hides the drawer. The drawer resizes from its top edge (double-click restores 240px), keeping 160px above it; maximize hides the page above it.
- A finished bash row shows **Open in terminal** on hover. It opens a new terminal and types the command at the first prompt **without running it**. Text is pasted with bracketed paste once the shell turns that on; a shell without bracketed paste gets single-line text after 2 seconds, and multi-line text is not typed there, because each newline would run a line.
- The status bar counts the selected session's terminals and names the shortcut.
- `terminal.shell` (Settings → PI DESKTOP → Terminal) names the program new terminals run; Automatic is the login shell.
- Limits: no search, no links to files (URLs open with Cmd/Ctrl-click), no per-tab rename; apart from the shell, Zed's terminal defaults apply (scrollback, `option_as_meta`). Terminals are not restored after restart. Exiting a shell is detected by the running app; under GPUI's test executor on Linux the child exit is not reported (Zed's own exit test is macOS-only), so the tests cover keys, output, paste, the drawer and the bash row, and `exit` was checked in the app under Xvfb.

## Language-server errors for pi (`pi_lsp_bridge`)

pi has no LSP support; the desktop runs the language servers (through `pi_editor`'s Zed `Project`). Without feedback, pi learns about a type error only when it runs a build. Example: pi changes `fn open(path: &str)` to `fn open(path: &Path)` in `session.rs`; `session.rs` is fine, but three callers in `desktop.rs` no longer compile. With the bridge, the `edit` result pi receives ends with:

```text
New errors in other files:
  src/desktop.rs:88:20 mismatched types
```

How it gets there, without changing pi:

- `crates/pi_lsp_bridge/extension/pi-desktop-lsp.ts` is a pi extension. Each `SessionController` starts a `Bridge` and writes the extension to the desktop data directory; pi is launched with `-e <extension>` and the bridge's address in `PI_DESKTOP_LSP`. Without the variable the extension does nothing. On macOS and Linux the address is a Unix socket in a private temporary directory, whose permissions keep other users out. On Windows, which has no Unix sockets in Rust's standard library, it is `tcp:<port>` on 127.0.0.1; any local program can reach a port, so every request must carry the random per-session token from `PI_DESKTOP_LSP_TOKEN`. Both transports build on every platform, so the Linux tests cover the TCP path too. One JSON line per connection: `{"op":"file","path"}` or `{"op":"run_end"}` in, `{"text"}` or `{"error"}` out.
- After a successful `edit` or `write`, the extension asks about that file and appends the answer to the tool result. When a run ends (`agent_before_settle`, not after an abort), it asks once more and adds a non-empty answer as a displayed custom message (`customType: "pi-desktop-lsp"`), which the model sees with the next prompt. `pi_core` shows such messages live from `entry_appended`.
- `Checker` answers from the session folder's project, found through `pi_editor::language_project`: only a project that is open and trusted, so language servers run only after the user started them in the Files view. Otherwise every answer is empty and immediate. Files whose type has no language server are answered at once too.
- The same connection carries the session's other requests. `Bridge::start` takes a `Handler`; `serve` sends every request whose `op` is not `file` or `run_end` to it: jj snapshots around `bash` and the jj tools (see "jj in the app").
- The desktop settings `languageServers.afterEdits` and `languageServers.beforeRunEnds` (overridable per project) turn each kind of answer off. `Bridge::start` takes them as an `allow` callback, read per request, so a change applies to running sessions. A turned-off request still attaches the checker to the project, so a run end sees files that a skipped file check changed.
- A changed file reaches its servers as an editor save would: its buffer is opened and registered with the servers, reloaded from disk, then `didSave` (`LspStore::on_buffer_saved`), plus a diagnostics pull for servers that are asked rather than push. A reload alone sends only `didChange`, and rust-analyzer starts `cargo check` on save. Up to 64 such files stay open in the servers, because many servers only diagnose open files.
- Waiting: servers send nothing when a file's errors did not change, so an answer waits until no server is busy (`has_pending_diagnostic_updates`, `pending_work`), nothing arrived for 300 ms, and either this file's diagnostics updated or 1 s passed. A file answer waits at most 4 s and a run end at most 20 s; the answer then names the servers still checking.
- What is reported: errors only (no warnings), primary diagnostics, first line of the message, 10 per section. A file answer lists all of that file's errors, says when a file that had errors has none, and lists new errors in other files. A run-end answer lists new errors anywhere; it first sends files that changed on disk without an `edit` or `write` answer covering them (for example from `bash`), up to 20 per run. "New" means not already told to pi and not present when the bridge first ran; errors are matched by file and message, not line, because lines move when a file changes. Files with unsaved edits in an editor are left out: their diagnostics describe the unsaved text.
- Tests: `cargo test -p pi_lsp_bridge --features fake-lsp` checks answers against Zed's fake language server and FakeFs (a server that, like `cargo check`, reports errors across files on open and save). Those are Zed test-support features; unified into `cargo test --workspace` they break Zed's `workspace` crate that `pi_editor` links, so CI runs them as a separate step. The default tests cover both transports, the token check, the installed extension and the "no language services" answer; the extension itself was checked in pi's faux-provider harness and loader.
- Limits: identical messages in one file count once. Changes made before language services were started are not tracked. Timing is heuristic; a slow `cargo check` can land after the run ends and is then reported at the next answer.

## App views: All Sessions, Models, Resources and Settings

The sidebar's app rows implement design study 02, screens 07–10. `WorkspaceController::view` holds the open one; it takes the middle column and the inspector instead of the active session, the header shows its title, and selecting a session leaves it (`select` clears `view`). The header's search field filters the app view shown.

- **Models / Resources** share `app_views/catalog.rs` for controller binding, subscriptions, virtualized lists and confirmation policy, with separate `models.rs` and `resources.rs` projections/renderers. Each screen is a lazily retained entity; its `CatalogInspector` observes it directly, so selecting a row updates details without a shell redraw. Selection/project changes detach the previous controller and clear its projected rows. Hidden catalogs avoid content-driven work. No additional Pi process starts for these screens; without a matching open session they show an explicit unavailable state.
- **Models** requests `get_available_models`, `get_auth_providers`, `get_settings` and current-model thinking levels. Provider cards deduplicate OAuth/API-key entries; capabilities/prices are optional, so unknown and zero differ. The cycle comes from resolved `scopedModels` (empty means all). Saving a cycle confirms replacing patterns, including `:level` suffixes, with exact IDs. `set_model` switches only the selected session unless the separately confirmed default action sends `persist: true`. Thinking choices save a per-model preference, and only current-model supported levels are offered. Login returns to the session terminal with `pi` staged, not executed; users complete `/login` there and restart the session to reload credentials. No auth files or tokens are read by the app.
- **Resources** requests `list_packages`, `get_project_trust`, and `get_commands`. It binds the existing selected-project controller, including background sessions, without starting an inspection process. Loaded extensions/errors and context paths are reported by the SDK where available; command-derived metadata is the honest fallback. Unknown scopes remain unknown. Skills and prompts retain source information; this is not a complete contribution manifest. User scope has no settings preview; only Project → Extensions retains/parses the allow-listed project-settings preview. Header Refresh reads metadata only; confirmed Reload may execute loaded code. Context files, unreported contributions, and unchecked update availability are never invented. Install/remove/update/reload/trust require a live idle session and Cancel-default confirmation; callbacks recheck controller identity and readiness. Package operations use RPC, not constructed shell commands, and long operations do not use the normal request deadline. Changes do not silently reload extension code. Trust is saved for the next process, distinct from editor/LSP trust; project installs require this process to already be trusted. Confirmation overlays occlude background clicks and intercept global search/navigation shortcuts. Catalogs and session/terminal views share `components::notification_card` and dismissible deferred overlays instead of consuming table/transcript space. Closing rechecks the displayed message and catalog owner; errors remain preferred in catalogs. Effective trust and the saved decision are compared: matching values show an active status, while differing values offer a restart/re-evaluation hint. Reload success replaces the reload-needed notice.

- **All Sessions** (`app_views/sessions.rs`) lists `WorkspaceController::saved`, the merged `list_sessions` (`scope: all`) of the open pi processes, now with `created`, `messageCount` and `parentSessionPath`. Filters: all, the selected project, named; sorts: recent, name, messages. Unnamed sessions show their first message; a session open in a tab shows a dot, or a spinner while pi works. The inspector gives details, the first message, the file and actions. **Resume** opens it (or shows its tab); **Fork…** opens it on the Tree page, which forks from an entry; **Rename…**, **Export HTML** and **Share link…** go to the session's own pi when it is open and otherwise to a short-lived pi on that session (`session_actions::on_session`), after checking pi resumed the right session; **Clone** does the same and opens the copy; **Export JSONL** copies the session file through a save dialog; **Delete** asks first, refuses while the session has a tab, and runs `delete_session` from a pi started with `--no-session`, since pi will not delete the session a process has open. Share asks before uploading and copies the link.
- **Settings** (`app_views/settings.rs`) has two groups of categories. PI edits pi's `settings.json` for the user (`$PI_CODING_AGENT_DIR` or `~/.pi/agent`) or the selected project (`.pi/settings.json`). PI DESKTOP edits the app's own preferences (below), which no agent reads. Each group is a source: a schema plus a user and a project file; a setting and a category are identified by source and key, since both groups have a Terminal. User and Project are segments above both groups. Project scope lists only the desktop settings a project may override (jj and language servers); the other desktop categories are greyed and say so. Rows show "changed" in user scope, and "this project" or "inherits" in project scope, where the inspector also shows the user's value and resetting is **Remove override**. Desktop choices have labels (`alt` reads "While ⌥ is held"). A desktop change goes through `prefs::write`, so it applies at once; loading the view also hands the desktop files to `prefs`, so a hand edit applies once Settings shows it. The crate `pi_settings` owns files and pi's schema without GPUI: its schema (key, category, type, default, description, whether only the user file may set it) is generated from pi's `docs/settings.md` by `crates/pi_settings/gen_schema.py`, so a new pi setting needs only a rerun; files keep unknown keys and their order, drop empty parent objects on reset, are written through a temporary file, and are never written when they do not parse (the error shows instead). Controls follow the type: toggles, segments for choices (thinking levels in their colors), a field for text, numbers and lists, a model picker for `defaultModel` from the open sessions' models, and "Edit in settings.json" for objects. A changed key shows a pill; the inspector shows the description, current, default and allowed values, the JSON it writes, the file, **Reset to default** (removes the key) and a link to pi's settings reference. Running sessions keep their settings; new sessions read the files. `Setting` and `SettingsFile` know no pi keys: `changed` takes a schema, `accepts` checks a value's type, and the temporary file is named after the file it replaces.

## Desktop preferences (`prefs`)

`crates/pi_desktop/src/prefs.rs` implements design study 06. It is separate from `pi_settings`' pi schema so other agents can be added later without touching it; it reuses `Setting` and `SettingsFile`.

- **Files.** User values: `settings.json` in the app's config folder (`~/Library/Application Support/pi-desktop` on macOS, `~/.config/pi-desktop` on Linux, `%APPDATA%\pi-desktop` on Windows; `PI_DESKTOP_CONFIG_DIR` moves it). Project overrides: the project's `.pi/pi-desktop.json`, beside pi's `.pi/settings.json`, shared with everyone who opens the project. Remembered state: `state.json` in the config folder (open sessions, the active one, and repository roots where the jj offer got "Not now").
- **Schema** (`prefs/schema.rs`, by hand; `Scope::Any` marks what a project may override): General (`general.backend`, `general.node`, `general.reopenSessions`, `general.confirmClose`, `general.rememberDismissed`), Appearance (`appearance.theme`: system, evening, moonstone), jj (`jj.offer`, `jj.snapshotBeforeCommands`, `jj.tools`, `jj.turnBars`, `jj.parallelSessions`), Language servers (`languageServers.afterEdits`, `languageServers.beforeRunEnds`), Editor (`editor.fontSize`, `editor.problemCard`), Terminal (`terminal.shell`). There is no text size: UI sizes are fixed pixels, which needs a refactor first. The jj settings drive the features under "jj in the app".
- **Resolution.** `Prefs` is a GPUI global loaded at launch (a small blocking read). `prefs::get(cx, key, project)` returns the project file's value for an overridable setting, else the user file's, else the default; a value of the wrong type counts as unset. A project's file is read once, when its first session starts (`prefs::load_project`, like jj's detection). Without the global, as in most tests, every value is its default and nothing is written.
- **Saving.** Each file has a `Writer`: saves run off the UI thread, never overlap, and always write the newest pending snapshot, so an older write cannot land after a newer one. Files that do not parse are shown and never written, as for pi's.
- **When settings apply.** At once: theme (`Desktop` observes the global and the window appearance, reacting only to a change, since GPUI also calls the observer when a window opens; System follows the OS; `--light` still forces Moonstone for the run; Ctrl+Shift+T switches until the next launch or theme change), editor font size (file tabs' text style, 8 to 32 px; the default 11.5 is what the tabs always used, not Zed's 15), problem card (`pi_editor::set_preferences` sets Zed's `hover_popover_enabled`; off shows Zed's hover popovers), close confirmation, language-server checks, turn bars. For new sessions: backend and Node, also for the short-lived pi processes of All Sessions and forks (`session_actions` take the backend). For new terminals: the shell.
- **Backend.** `Launch::pi_with` takes `general.backend` and `general.node`: a `.js`/`.mjs`/`.cjs` path runs with Node, anything else runs as an executable, Automatic runs `pi` from PATH. `PI_DESKTOP_RPC_ENTRY` (with `PI_DESKTOP_NODE`) and `PI_DESKTOP_PI` still win. The inspector's FOUND section shows what an open session runs and its `get_backend_info` answer. Setup (study 07), Run setup again and the too-old check are not built yet.
- **Reopening sessions.** `WorkspaceController` saves the open sessions (folder, session file, id, name, title) and the active one whenever tabs, selection or a summary change; the demo never writes. At launch, with `general.reopenSessions` on, `main` reopens them; a session whose file is gone reopens as a new session in its folder, and a missing folder is skipped. `--project DIR` opens DIR as well; without saved sessions the app starts in the working folder as before.

## Attachments

pi's prompt carries text and images (`prompt` with `images`, also as steer or follow-up), and pi reads any other file itself. So the paperclip, a paste and a drop onto the composer split files in two (`desktop/attachments.rs`):

- PNG, JPEG, GIF and WebP images become attachments: a thumbnail chip above the draft with name, size and ×. They go with the prompt as base64 `ImageContent`; pi resizes them for the model when its settings say so. Images over 20 MB are refused with a notice. A pasted image (the clipboard's image entry) attaches instead of pasting text.
- Any other file becomes a file chip, as an `@` mention would: `@path` from the project root, or the whole path for a file elsewhere (quoted in backticks when it has spaces). pi reads it with its read tool, which handles text and images; PDFs and Office documents need a command-line tool such as `pdftotext`.
- `SessionController::submit_with` sends text, images or both; a prompt pi rejects returns its text as the draft (`RecoverDraft`) and its images as attachments (`RecoverImages`). Queued messages pi hands back on Stop carry text only.
- When the selected model's `input` lacks `image`, the attachment row says the model will not see them; the prompt still goes.
- Sent messages show their images under the text, decoded once per message. In demo mode a submitted message has text and image blocks, as pi's user messages do.

## @ mentions

Typing `@` in the composer opens one grouped menu above it (design study 08); what follows the `@` filters it. A choice becomes a chip in the draft, and the sent message shows the chip again. Example: the draft "Compare `[file] opencode.ts` with its tests" reaches pi as `Compare @packages/ai/src/providers/opencode.ts with its tests`.

- Groups, in this order and only when they have entries: **Files** (the project's files from the Files view's worktree, loaded on first use; files pi changed in this session first; five shown), **Symbols** (the language servers' workspace symbols, from two typed characters and after a 150 ms pause), **Turns** (this session's jj turns), **Sessions** (saved sessions other than this one), **Terminal** (each shell's last 40 non-empty lines), **Problems** (files with language-server errors or warnings). Symbols and problems need language services to be trusted. Matching is fuzzy: a run of letters beats scattered ones, file names beat paths, and matched letters are highlighted. The highlighted file shows a preview beside the menu: its path, size, language and first lines, read off the UI thread.
- Matching uses Zed's standalone `fuzzy` crate: `match_path_sets` over the existing Files/worktree projection for paths and `match_strings` for symbols/turns/sessions/terminal/problems. It runs on background tasks with cancellation and query/range/generation guards; stale results cannot replace the current menu or reopen a dismissed one. No Zed Workspace, filesystem scan or inspection process is introduced. Empty-query display order remains owner-preferred; nonempty queries use Zed scoring and UTF-8 byte highlights.
- **Directories** come from the same existing Files/worktree snapshot (five shown), with folder icons and trailing slashes. Exact directory names/trailing-slash queries prioritize that group. They are references only: no file preview read, recursive expansion or contents attached. Directory chips send `@path/` (backtick-quoted for spaces), and sent directory links reveal the folder in the Files inspector, not a file editor. The list is viewport-bounded and keyboard selection scrolls into view; Unicode highlights use character boundaries.
- Keys: ↑↓ select, ⏎ inserts a chip, ⇥ writes a file, directory or symbol out as text (`@path`) instead, Esc dismisses the menu for that `@`.
- Chips live in `TextInput` (`input.rs`): an atomic range whose text is an em space and a hair space (room for the icon) and the label, with non-breaking spaces. The cursor never stops inside one, an edit touching it removes all of it, and it is drawn as a rounded, bordered box per row it wraps across, with its icon over the lead spaces and the label in the mono font. The composer keeps what each chip stands for (`mentions::Mention`) by chip id.
- What pi receives (`mentions::prompt`) is plain text and hides nothing. Files are `@path`, pi's own convention (its file tools strip the `@`); symbols are `name (@path:line)`. Terminal output, problems, turns and sessions are text: `[kind: title]` in the sentence and a `<mention kind="…" title="…">` block after the message. A problems chip reads its file's diagnostics when chosen; sending waits for that.
- The transcript finds mentions in sent messages again (`mentions::parse_sent`), also after a reload: `@path` and `name (@path:line)` become links around inline code, which Zed's Markdown draws as rounded chips, colored by a `link_callback` for `pi-mention:` links. The trailing blocks leave the visible text; their chips show or hide the text pi received under the message. A file chip opens the file in a file tab. Code spans and fences are left alone.
- The inspector's overview lists the draft's chips under IN THIS PROMPT with what pi gets for each ("path · pi reads it", "text · 3 lines"). The composer tells it through `ComposerEvent::Mentions` only when the chips change, so typing does not render the inspector.
- Limits: chips in sent messages have no icon (Zed's Markdown chips hold text only); the editor selection is not offered yet; `@` works in the composer only, not yet in an editor tab's prompt line.

## Boundaries and remaining work

`pi_editor` now embeds Zed's `Project`, `Editor` and `languages`, without creating a Zed `Workspace`. A lazy service registry shares project entities by canonical root; session-local `FilesView`s own tabs over those shared buffers. Live opens validate regular/text-sized files off the UI thread. Disk conflicts block save; reload/discard and project trust require confirmation. The editor database and language-server packages use a separate pi-desktop data directory, not Zed's database/configuration. NodeRuntime currently retains Zed's npm-cache location. Language services are an explicit project-trust opt-in, can execute project configuration/download server packages, and require an existing Node installation where applicable. No hosted Zed authentication/connection or telemetry startup is performed.

The native offline preview is read-only and labeled. Live file actions are separate: New File/New Folder, rename, and confirmed system-trash deletion run through `pi_editor::file_actions`. Creation uses atomic no-overwrite operations (not Zed's truncating create-entry helper); paths stay inside the project and `.git`/`.jj` are protected. Rename/trash recheck shared dirty buffers before executing. Dialog inputs stay mounted during async work so errors cannot lose keyboard focus. The file browser has its own focus boundary; its menus/dialogs must not send editor keystrokes or session-stop commands.

The embedding CLI implements Zed's internal `--printenv` probe before GUI/RPC initialization. `diagnostics::init` registers Zed's diagnostic renderer, without a Workspace instance, so LSP diagnostic hover/inline blocks can render. Registering Editor alone is insufficient and caused `no rendered diagnostic` errors. npm installs still follow the user's npm registry configuration; this adapter does not replace it.

**Problem card.** Zed shows a diagnostic and the language server's hover text as two separate popovers, the diagnostic one a pink box with Zed's own wording. The file tab shows one card instead, as in design study 05: the message with its code (`ts(18048)`), the hover text's code lines, then the first quick fix and **Ask pi to fix**, with the key hints.

- `pi_editor` turns Zed's hover popover off (`hover_popover_enabled: false` as user settings) and `pi_editor::problems` supplies the pieces: `point_at` and `below` map between window pixels and text positions, `problem_at` picks the most severe primary error, warning or note (hints stay underlines), and `hover_text`, `quick_fix` (the first `quickfix` code action) and `apply_quick_fix` (undoable, left unsaved) ask the project's language servers.
- Zed keeps its editor's pixel-to-text map private, so `point_at`/`below` repeat its element's arithmetic from public pieces: `last_bounds`, the gutter dimensions, the scroll position and the line layout. A Zed update that changes that layout needs the same change here.
- `files/card.rs` shows the card 300 ms after the pointer rests on a problem (or on a word, for plain hover text) and hides it 300 ms after the pointer leaves both text and card, so the pointer can cross the gap; scrolling, editing, switching tabs and Escape hide it at once.
- **Ask pi to fix**, or ⌥⏎ (Alt+Enter) with the cursor on a problem, sends "Fix this language server error in `path:line:col`:" and the message through the session's normal submission, then shows the thread; the open file reloads when pi edits it. If pi cannot take a prompt at that moment, the text becomes the composer's draft. ⌘. (Ctrl+.) opens Zed's code-action menu with every fix.

The composer remains the lightweight multiline GPUI input, now with `@` mention chips (above). Per-file jj restoration, prompts from an editor tab and broader cross-platform live-editor validation remain unfinished.

Standard confirm/select extension requests use a bounded session-local FIFO (16 requests), Cancel-default native prompts and exact correlated responses. The originating controller/session is rechecked; switching tabs cannot answer another request. Backend timeout/abort/disconnect cancels active/queued dialogs. Unsupported input/editor requests cancel with a notice. Extensions own these policy decisions: Pi trust is not an OS sandbox and no per-extension filesystem/network grants are invented. Status and notifications are displayed; custom TUI widgets are not implemented.

Full git/worktree/tree workflows, native authentication dialogs, complete loaded-resource manifests, and idle-process/document-cache eviction remain follow-up work. Sidebar rows are not virtualized. Fixture data is always labelled and never substituted for missing live data.

## Planned direction

Agreed with the user. jj turns, the three session views, embedded file tabs and the terminal drawer are now being implemented (above), and so are @ mentions in the composer; per-file jj restoration remains planned. Shared tabs, Changes and editor layout follow `desktop-workspace-study.svg`; Tree content and Context follow `desktop-views-study-light.svg`. The existing left sidebar layout is preserved, with requested project selection and hover-only close controls.

- **jj first.** Projects use Jujutsu, colocated with git, as the version-control layer, so any agent change can be rolled back. Each agent turn that changes files becomes its own jj change, described with the prompt; turns that change nothing leave no trace. Rolling back a turn abandons that change, and `jj op log` / `jj undo` cover everything else. The Changes view then reads the turn's `jj diff` instead of observed edit/write calls. jj runs only between runs (after `agent_settled`), never while pi is writing. A GPUI-independent `pi_jj` crate drives it through `jj-lib` (Apache-2.0, pinned to an exact version because its API changes every release), so users need no installed `jj`. Each operation does what the jj CLI does around a command: load the user's jj config, snapshot the working copy, and in colocated repos import git refs before and export them after. jj-lib's API is async; it runs off the UI thread. A project without jj gets an explicit prompt to run `jj git init --colocate`; nothing is initialized silently.
- **Files and editing.** A file tree and tabs of our own over Zed's `project::Project` (worktrees, buffers, file watching) and `editor::Editor`, with language servers from Zed's `languages` crate, rather than hosting Zed's `Workspace`. pi's edits on disk reload open buffers, and unsaved-buffer conflicts are surfaced rather than overwritten. First step: open a changed file in an `Editor` with its language server running.
- **Terminal.** Zed's standalone `terminal` crate (alacritty, PTY) with a view of our own adapted from `terminal_view`'s `TerminalElement`, which requires a `Workspace`. Implemented as `pi_terminal` and the session's terminal drawer (above).
- **Language-server feedback.** Implemented as `pi_lsp_bridge` (above) for `edit`/`write` results and run ends. Next: model-callable tools registered by the same extension (`lsp_diagnostics`, `lsp_definition`, `lsp_references`, `lsp_hover`, `lsp_symbols`, taking a file plus a symbol name or line rather than a column). Automatically continuing a run to fix reported errors (`agent_before_settle` with `continue`) is left out because it can loop.
- **@ mentions.** Implemented in the composer (above). Still planned: the editor selection as a mention, and `@` in an editor tab's prompt line.
